# 设计说明

## 1. 需求拆解

题目最核心的不是页面数量，而是一条消息的生命周期：

1. 用户输入消息。
2. 前端知道消息属于哪个会话，并把消息发送到后端。
3. 后端检查发送者是否属于该会话。
4. 后端保存消息。
5. 后端把新消息推送给在线用户。
6. 前端收到后更新界面。
7. 页面刷新后，前端重新从后端读取历史记录。

## 2. 前后端职责

前端只负责展示和交互：登录表单、用户搜索、会话列表、消息列表和发送表单。前端不把消息历史当作可靠存储，刷新后会重新请求后端。

后端负责数据和规则：用户、会话、消息的增删查，成员校验，消息持久化，以及向在线用户推送新消息。

## 3. 数据模型

`users` 保存用户：

```json
{
  "id": "用户唯一 ID",
  "username": "昵称",
  "createdAt": "创建时间"
}
```

`conversations` 保存一对一会话：

```json
{
  "id": "会话唯一 ID",
  "userIds": ["用户 A", "用户 B"],
  "createdAt": "创建时间"
}
```

`messages` 保存消息：

```json
{
  "id": "消息唯一 ID",
  "conversationId": "所属会话",
  "senderId": "发送者",
  "content": "正文",
  "createdAt": "发送时间"
}
```

## 4. 为什么选择 SSE

本项目使用 SSE 的原因是：浏览器原生支持 `EventSource`，服务端实现也很短，适合第一次理解“服务器主动通知浏览器”。它是服务端到客户端的长连接，客户端发送消息仍然使用普通 HTTP POST。

这不是唯一方案。WebSocket 可以同时支持双向长连接，更适合高频互动和复杂状态；但它需要额外的协议和连接管理。对于本题的小型一对一聊天室，SSE + POST 已经能完整表现消息从发送到保存再到显示的过程。

## 5. 关键 API

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/users` | 创建或进入一个昵称 |
| GET | `/api/users` | 搜索其他用户 |
| GET | `/api/conversations` | 获取当前用户的会话 |
| POST | `/api/conversations` | 创建或复用一对一会话 |
| GET | `/api/conversations/:id/messages` | 获取历史消息 |
| POST | `/api/conversations/:id/messages` | 保存并发送消息 |
| GET | `/api/events` | 建立 SSE 实时推送连接 |

## 6. 答辩问题准备

### 为什么消息不能只放在前端？

前端内存刷新就会消失，浏览器本地存储也不方便让两个用户共享。后端保存后，任何一方刷新都能重新读取同一份历史记录。

### 为什么要先保存再推送？

如果先推送后保存，可能出现用户看到了消息但服务器没有记录的情况。先保存成功，再广播，可以让“看到的消息”与“可恢复的消息”保持一致。

### 为什么需要会话 ID？

用户之间可能存在多条消息。会话 ID 把属于同一次聊天的消息归到一起，前端打开会话时只查询对应的消息。

### 如何防止陌生人向别人的会话发消息？

后端收到消息后，根据会话 ID 找到会话成员，再检查 `senderId` 是否属于 `userIds`。前端校验只能改善体验，真正的权限校验必须放在后端。

### 这个项目还能怎样改进？

可以加入真正的密码登录、SQLite/MySQL 数据库、WebSocket、群聊、未读消息、分页加载和部署配置。升级时仍然保留现在的核心流程：接收、校验、保存、推送、恢复。
